PARTE 4: MATRIZ PROFUNDA DE RIESGOS, DEBILIDADES Y PLANES DE MITIGACION
================================================================================

Riesgo A: Duplicidad Estructural y Ruptura Masiva de Imports (Severidad: Critica)
- Descripcion del Riesgo:
  Si el PR #5 se fusionara directamente hacia main sin mediación, el repositorio tendría al mismo tiempo la carpeta "src/" (con la lógica RAG, ingestión y cliente OCI) y una nueva carpeta "backend/".
- Causa Raiz:
  Desalineación entre la convención técnica de Ingeniería de Datos y el modelo mental de desarrollo Web Full Stack.
- Impacto Tecnico:
  Ruptura inmediata de rutas en sys.path, inconsistencias severas en tests de pytest, duplicidad innecesaria de archivos __init__.py y colapso de integración para los desarrolladores de frontend al intentar consumir servicios inexistentes en su ruta esperada.
- Plan de Mitigacion y Solucion:
  Implementar la convergencia arquitectónica adaptativa (ver Parte 6), trasladando la lógica de negocio validada al contenedor unificado "backend/", garantizando compatibilidad absoluta y eliminando carpetas redundantes.

Riesgo B: Incompatibilidad Operativa en el Contenedor Docker PR #3 (Severidad: Alta)
- Descripcion del Riesgo:
  El Dockerfile presentado en el PR #3 fue concebido sin conocer la ubicación final de los scripts ejecutables y las dependencias consolidadas.
- Impacto Tecnico:
  Si el contenedor intenta ejecutar "uvicorn backend.main:app" o "streamlit run ui/app.py" sin una jerarquía de archivos homologada, el contenedor crasheará al iniciar (Container Exit Code 1 / ModuleNotFoundError).
- Plan de Mitigacion y Solucion:
  Condicionar la aprobación del PR #3 a las siguientes especificaciones técnicas de ingeniería:
  1. Uso de imagen base oficial ligera: python:3.11-slim.
  2. Configuración para instalar las dependencias específicas de backend y frontend.
  3. Exposición correcta de puertos: 8501 (Streamlit UI) y 8000 (si se exponen endpoints REST).
  4. Entrypoint flexible y reproducible.

Riesgo C: Vacio de Pruebas Automatizadas en Nuevas Ramas (Severidad: Media)
- Descripcion del Riesgo:
  Los desarrolladores están abriendo Pull Requests sin adjuntar sus correspondientes casos de prueba dentro de la carpeta tests/.
- Impacto Tecnico:
  Riesgo de regresión silenciosa sobre los módulos de ingestión, chunking y almacenamiento Always Free de OCI que ya cuentan con pruebas unitarias operativas en el baseline de Martin.
- Plan de Mitigacion y Solucion:
  Establecer como regla de Definition of Done (DoD) que todo PR técnico debe incorporar al menos una prueba unitaria con pytest que valide la funcionalidad agregada antes de poder ser fusionado.

PARTE 6: LA RESOLUCION ESTRATEGICA — EL ENFOQUE ADAPTATIVO
================================================================================

Analisis Adversarial y Choque de Paradigmas:
- Paradigma Normativo (Ingeniería de Datos / IA en Python):
  Estructura estándar de biblioteca o paquete monolítico: "src/" para la lógica del sistema y "ui/" para la interfaz gráfica.
- Paradigma Bootcamp / Web Full Stack:
  Estructura clásica mental grabada en desarrolladores de Alura y No Country: "backend/" (lógica, servicios y persistencia) y "frontend/" (interfaz de usuario).

La Decision Estrategica del Project Manager Martin Morfe:
El liderazgo de excelencia no consiste en imponer una nomenclatura semántica a costa de la desmotivación del equipo. Consiste en adoptar el modelo mental que el equipo domina ("backend/" + "frontend/"), integrando dentro de esa estructura toda la robustez técnica previamente construida (contratos Pydantic, prompts taxonómicos de Bloom, almacenamiento seguro en OCI Always Free y ChromaDB).

Arquitectura Fisica Definitiva y Unificada:

G10-team1-newmind/
├── backend/
│   ├── ingestion/       (Extractores PDF/Markdown y chunking semántico con overlap)
│   ├── rag/             (ChromaDB vectorial, generación de embeddings y retriever)
│   ├── llm/             (Adaptadores Gemini/OpenAI, orquestador y prompts pedagógicos)
│   ├── storage/         (Cliente OCI Object Storage Capa Always Free)
│   ├── models/          (Contratos de datos con Pydantic y validación estricta)
│   ├── config/          (Configuración centralizada y variables de entorno .env)
│   ├── requirements.txt (Dependencias de procesamiento, IA y cloud)
│   └── main.py          (Punto de entrada o dispatcher de servicios del backend)
│
├── frontend/
│   ├── app.py           (Aplicación interactiva construida en Streamlit)
│   ├── assets/          (Hojas de estilo CSS y recursos visuales institucionales)
│   └── requirements.txt (Dependencias exclusivas de interfaz gráfica)
│
├── docs/                (Plan PRINCE2, WBS de 5 Sprints, Requerimientos ONE G10 y Tarea 1)
├── data/samples/        (Manuales y guías técnicas de prueba para ingestión)
├── tests/               (Suite completa de pruebas automatizadas con pytest)
├── docker-compose.yml   (Orquestación conjunta de contenedores backend y frontend)
└── Dockerfile           (Construcción reproducible del entorno)

Redignificacion de los Pull Requests #3 y #5:
- El PR #5 deja de ser un intento de bifurcación conflictiva y se convierte en la fundación oficial de la carpeta "backend/".
- El PR #3 adquiere su propósito definitivo: levantar el contenedor Docker apuntando a la nueva estructura "backend/" y "frontend/".
